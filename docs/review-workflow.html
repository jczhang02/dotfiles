Agent 改, 我来看: git review 工作流

Claude 在一个 pane 里改文件, 你在旁边的 pane 里看. 这份教程告诉你在每个时刻, 每个 repo 里该运行哪个命令, 按哪个键, 以及该对 agent 说什么.

目录

    先记住 3 条

    1. review 发生在 4 个时刻. agent 改的时候, commit 之前 (A), 合并之前 (B), 事后 (C). 每个 repo 的 git 规则决定你主要在哪个时刻看: agent 不能自己 commit 的 repo, 重点在 A; agent 可以自己 commit 的 repo, 重点在 B 或 C.
    2. 和 main 对比, 只用三个点. 用 git diff main...HEAD 或 git diff --merge-base main, 不用 git diff main. 分支落后 main 时, 两个点会把 main 的新内容显示成 "你删掉的".
    3. 只看用 shell, 要动手用 nvim. hunk 和 delta 只能看. 要编辑, 选一部分 stage, 或解决冲突, 用 nvim 里的 diffview, fugitive 和 gitsigns.

    工作台

    tmux session: monge-ampere-equations · window: monge-ampere-equations/flow1-exp
    pane 1: Claude Code在 worktree 里改文件, 运行 just check, 等你说 "commit".
    pane 2: shellgit diff 打开 hunk, agent 写文件时自动刷新. 也用来运行 wt, git log.
    nvim (同一个 window 的另一个 pane, 或另一个 window)文件被 agent 改了会自动重新载入. 用 Space g 开头的键做 stage, 分支 review 和冲突处理.

    一个 repo 一个 session, 一个 worktree 一个 window.

    • session: 按 C-Space s 用 sesh 选 repo, 按 C-Space S 回到上一个 session.
    • window: tmux-autoname 会把 window 名改成 repo/branch. 所以 shell cd 进 worktree 后, 你在状态栏就能看到自己在哪个分支.
    • agent 看不到 hunk. agent 自己运行 git diff 时没有终端, 不会打开 hunk, 输出的是普通文本. [pager] diff = hunk pager 只对你有效.
    • 不要在 Claude 输入框里用 ! 运行 hunk 或 nvim. 它们是交互界面, 在 Claude 里打不开. 请在 pane 2 里运行.

    4 个时刻, 各用什么

    时刻你要回答的问题shellnvim
    0 改的时候agent 现在在改什么?git diff不用操作, 自动重新载入
    A commit 前哪些改动要留下?git diff
    git diff --staged    		Spacegg, ]h + Spaceghs
    B 合并前这个分支一共会给 main 带来什么?git log --oneline main..HEAD
    git diff main...HEAD
    git diff --merge-base main    		Spacegm, SpacegM
    C 事后某个 commit 做了什么? 这行是谁改的?git show <sha>
    git rs <sha>
    git log -p    		Spacegf, Spaceghb

    git log 的两个点和 git diff 的三个点不矛盾. git log main..HEAD 列出 "在 HEAD 上, 不在 main 上" 的 commit, 这正是分支自己的 commit. git diff 的两个点意思不同, 它直接对比两个端点, 所以会混入 main 的新内容.

    按 repo 的流程

    每个 repo 的 CLAUDE.md 或 AGENTS.md 写了 agent 能自己做什么. 这决定你在哪个时刻 review. 下面每个 repo 先列规则, 再列流程, 最后列可以直接发给 Claude 的话.

    monge-ampere-equations: 论文和研究代码

    规则 → 重点在时刻 A

    必须在 .worktrees/ 里工作, 不在主树切换分支. agent 在 commit, push, 开 PR, merge, 打 tag 之前都要问你. CI 不检查 push 和 PR, 所以本地要运行 just check 和 just pdf <dir>. LaTeX 和 Markdown 一句一行.

    1. 开始一个任务

    • 你的习惯是让 agent 自己建分支. 告诉它分支名, 它会建 .worktrees/<branch-with-dashes>.
    • 自己开也可以: wt switch -c fix/xxx. 这会从 main 建分支, 把 worktree 放在 .worktrees/fix-xxx, 并把当前 shell cd 进去.
    • 已经有的 worktree: wt switch flow1-exp, 或者只输入 wt switch, 从列表里选.

    2. agent 改的时候

    1. 在 pane 2 里进入同一个 worktree, 运行 git diff.
    2. 按 ] [ 跳 hunk, 按 . , 换文件. LaTeX 长行会自动换行, 按 w 切换.
    3. 看到问题, 按 c 写 note, 按 Ctrl+Enter 保存. 这时先不要退出 hunk.
    4. 对 Claude 说下面的第一句. 它会用 hunk session comment list 读到你的 note.

    3. agent 问 "要 commit 吗?" 的时候 (时刻 A)

    1. 全部改动都要: 在 hunk 里看完, 再看 agent 是否运行了 just check 和对应的 just pdf. 都通过就回复 "commit".
    2. 只要一部分: 在 nvim 里按 Spacegg, 在文件上按 = 展开, 在想要的 hunk 上按 s. 然后告诉 agent 只 commit 已 stage 的部分.
    3. 想自己改几个字: 直接在 nvim 里改, 保存后告诉 agent "我改了 X 文件, 一起 commit".
    4. 新建的文件 (??) 不会出现在 git diff 里. 要看就先 git add -N <path>, 或者在 nvim 里用 Spacegd.

    4. 跑服务器实验之前

    MLflow 会记录实验用的 commit, 以及工作区是否有未提交的改动. 所以要先 review, 再 commit, 然后才 just push 和 just remote .... 不要先跑实验再回头改代码.

    5. 合并到 main 之前 (时刻 B)

    1. wt list: 看 main↕ 这一列. ↑80 ↓60 的意思是分支有 80 个 main 没有的 commit, 同时落后 main 60 个.
    2. 在 nvim 里按 Spacegm: 只显示分支自己的改动. 右边是磁盘上的文件, 可以直接改.
    3. 想按 commit 看: SpacegM.
    4. 确认后, 明确告诉 agent merge. 这一步必须由你说出来.

    6. 合并之后

    wt remove fix/xxx: 删除 worktree. 分支已经合并时, 它会一起删掉分支. 分支还没合并时, 分支会保留, 要删得加 -D. 然后关掉对应的 tmux window.

    可以直接对 Claude 说

    • 读我在 hunk 里写的 note, 逐条修改, 改完告诉我每条怎么处理的.
    • 在新 worktree 里做: 分支 fix/flow1-tables, 从 main 开.
    • 只 commit 已经 stage 的部分, 不要再 git add.
    • 把你的每处改动的理由写成 hunk note. (要先在 pane 2 打开 hunk, 然后按 a 显示 agent 的 note.)
    • build writing/reports/midterm, 再 just check, 都过了再问我 commit.

    maesolvers: Python 求解器库

    规则 → 重点在时刻 B 和 PR

    必须用 worktree. agent 可以自己 commit, push 分支, 开 PR, 不用问你. 要问你的是: merge 进 main, 打 tag, 改已 push 的 commit, 改固定的复现数值, 改已接受的 ADR. 有依赖关系的一串 PR 用 gh stack.

    流程

    1. 开始: 和 monge 一样, 让 agent 建 worktree, 或用 wt switch -c.
    2. 改的时候: agent 会自己 commit, 所以 git diff 经常是空的. 改用 hunk diff main...HEAD 看整个分支, 按 r 刷新.
    3. 看 agent 的每个 commit: 在 nvim 里按 SpacegM, 或在 shell 里运行 git rs (hunk 显示最新的 commit).
    4. PR 开了以后: hunk gh pr <编号> 在 hunk 里看 GitHub 上的 PR. 想让另一个 agent 帮你看, 在 Claude 里运行 /code-review.
    5. 合并: 你看完后说 "merge PR #N". 合并后 wt remove.

    实验: 和 monge 相同, 先 commit 再 just push. 不同点: maesolvers 在服务器上每个分支有自己的 worktree, 路径是 /jczhang02/maesolvers-wt/<branch>.

    可以直接对 Claude 说

    • 把这个改动拆成 3 个依赖的 PR, 用 gh stack.
    • /code-review since main
    • PR #12 的第 2 个 commit 改错了, 新加一个 commit 修复, 不要 amend.

    dotfiles: 配置

    规则 → 重点在时刻 C

    直接在 main 上工作. agent 验证完就 commit 并 push, 只 stage 和任务有关的文件. 要改 repo 里的文件, 不改 $HOME 下的 symlink 路径. nvim/.config/nvim 是 submodule: 先在里面 commit 和 push, 再在 dotfiles 里 commit 指针.

    流程

    1. 看 agent 刚做了什么: git log --oneline -5, 然后 git show (delta) 或 git rs (hunk). 两个都默认显示最新的 commit.
    2. nvim 配置的改动: dotfiles 里的 commit 只显示 "Subproject commit" 指针变了. 要看内容, 进入 nvim/.config/nvim 再 git show.
    3. 不满意: 对 agent 说 "revert <sha>". 已 push 的 main 不能改写, 所以撤销是新加一个 revert commit. 之前 tmux 鼠标设置就是这样撤销的.
    4. 你自己的未提交改动 (mise, zsh 等) 会一直留在 git status 里. agent 不会动它们. commit 前想确认, 运行 git diff --staged.

    可以直接对 Claude 说

    • 撤销你刚才的 tmux 改动, 用 revert.
    • 改 nvim 配置, 记得 submodule 先提交.

    blog 和 partjobs

    规则 → 重点在时刻 A

    这些 repo 只要求 Conventional Commits, 没有 worktree 规则. Claude Code 默认只在你说了以后才 commit, 所以流程和 monge 的时刻 A 一样: git diff 看, 回复 "commit".

    • blog: .gitattributes 让 About 文件夹的文字不出现在 git diff 里. 所以 hunk 里看不到那里的改动, 这是故意的. 看页面效果用 bun run dev.
    • partjobs: ~/dev/partjobs 本身不是 git repo, 每个子目录才是. 你常从 ~/dev/partjobs 启动 Claude, 所以先 cd 进子目录再运行 git diff.

    常见情况

    分支落后 main 很多

    main:       ──M──m1──m2── … ──m60
                \
flow1-exp:       f1──f2── … ──f80  + 未 commit 的改动

    M 是 merge-base: 分支从 main 分出去的那个 commit. 用 git merge-base main HEAD 查.

    命令从 → 到显示
    git diff mainm60 → 工作区f1-f80, 未 commit 的改动, 还有 m1-m60 的反向内容. 不要用.
    git diff main...HEADM → f80只有分支的 commit. Spacegm 用的就是这个.
    git diff --merge-base mainM → 工作区分支的 commit 加上未 commit 的改动.

    想让分支跟上 main, 对 agent 说 "把 main merge 进这个分支". 在 monge 里 rebase 已 push 的分支要先问你, 所以 merge 更省事.

    merge 有冲突

    1. 在 nvim 里按 Spacegd. 冲突的文件会打开 3 个窗口.
    2. ]x / [x 跳到下一个 / 上一个冲突.
    3. 选一个版本: Spaceco ours, Spacect theirs, Spacecb base (共同祖先), Spaceca 全部保留, dx 整块删除.
    4. 冲突标记是 zdiff3 格式, 中间的 ||||||| 段是 base 的内容. 看它就知道两边各改了什么.
    5. 在文件列表里按 - 标记为已解决, 再让 agent 完成 merge commit.

    你和 agent 用 hunk note 来回讨论

    1. 你: 在 pane 2 里运行 git diff, 按 c 写 note, 按 Ctrl+Enter 保存.
    2. agent: 对它说 "读我在 hunk 里的 note". 它会运行 hunk session comment list --repo . --type user.
    3. agent 也可以反过来写 note: hunk session comment add. 你按 a 显示 agent 的 note.
    4. note 只在 hunk 运行时存在. 退出 hunk, note 就没了. 所以要先让 agent 读完, 再退出.

    只看一个文件

    • shell: git diff -- path/to/file.
    • nvim, 当前文件对比 index: Spaceghd. 对比上一个 commit: SpaceghD.
    • nvim, 左边的 sign 改成对比 main: Spaceghm, 再按一次切回 index.

    找一个旧版本, 或找是谁改的

    • 当前文件的历史: Spacegf. 在列表里按 L 看 commit 说明, 按 y 复制 SHA.
    • 当前行是谁改的: Spaceghb. 整个文件: SpacegB.
    • 在终端里翻历史: hunk log, 或 git log -p -- path (delta).

    同时有好几个 worktree

    • wt list: 每个 worktree 的路径, 和 main 的差距, 是否有未提交的改动.
    • hunk status: 当前 repo 和它的所有 worktree.
    • 每个 worktree 开一个 tmux window. window 名就是 repo/branch, 用 C-Space 加数字切换.

    外观

    系统切换浅色 / 深色时, 所有工具都会跟着变, 你不用做任何事.

    • hunk 和 tmux: 读 Ghostty 的调色板, 立即切换.
    • nvim: tmux 的主题 hook 会通过 RPC 通知每个正在运行的 nvim. 只在 tmux 里有效.
    • delta 和 bat: 下一次运行命令时读取系统设置.
    • nvim 没有跟着变: 运行 ~/.config/tmux/nvim-theme.sh dark (或 light). 也可以在 nvim 里 :set background=dark.
    • 只改 hunk: 在 hunk 里按 t 选主题, 只对这一次有效.

    不要做的事

    1. 不要用 git diff main 或 :DiffviewOpen main 对比分支. 理由见 分支落后 main 很多.
    2. 不要用 wt merge. 它默认会 squash, rebase, stage 全部文件, 然后删除 worktree, 和 repo 规则冲突. 合并让 agent 做, 或者开 PR.
    3. 不要在 monge 和 maesolvers 的主树里 git switch. 换分支就换 worktree: wt switch <branch>.
    4. 不要通过 $HOME 的路径改 dotfiles. sed -i 和 git config --global 会把 symlink 换成普通文件. 之前 ~/.gitconfig 就是这样和 repo 脱节的.
    5. 不要在 note 还没被 agent 读到之前退出 hunk. note 不会保存.
